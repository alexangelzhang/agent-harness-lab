# OpenAI Developers：为 GPT-6 Astra 重思 skills 与 prompts

来源：https://zhuanlan.zhihu.com/p/2099082430485475391（转载翻译，原文：Rethinking skills and prompts for GPT-6 Astra，Eric Provencher，OpenAI Developers Blog，2026-09-11）

写作背景：模型变强后，过去大量「扶着走」的指令可能反而碍事。若过去一年用 Codex 一类 Agent 做项目，多半已堆了不少指令（skills、AGENTS.md、任务 prompt）；到了 GPT-6 Astra，重审这些假设比以往更重要。

## 更好的 skills

Skills 本质是存成 Markdown 的 prompt，也可打包资源和捆绑脚本，最适合特定工作流或某些应用上的指引。

常见问题：

- 描述太长。skill 一多，Codex 会缩短描述以塞进上下文，模型看到的每段更少，更难选对。
- 描述互相矛盾，或过度强调「何时该用」，导致模型加载对任务并无帮助的指令。

三条修正（来自更新后的 $skill-creator 指引）：

1. **描述尽量短，说清何时该用**。坏例子：「创建并校验 Postgres schema migration。在处理数据库、查询、模型或持久化时使用。」→ 模型会只要碰数据库相关就用。好例子：「创建并校验 Postgres schema migration。在新增/修改 migration 或评审其 rollout 时使用。」
2. **渐进披露是关键标志**。读 skill 占上下文、更靠近 compaction，还可能引入与当前任务无关的指引。多工作流的 skill，把根文档做成最小路由，指向辅助文档与脚本——让模型知道往哪找，而不强迫它当下读无关内容。
3. **别再写详尽菜谱**。模型已更擅长理解细微与模糊，过度具体的指引过去曾有帮助，现在可能妨碍结果。

另外：仓库 skill 也会引导其他贡献者的 Agent，对方可能用不同模型。帮 Sol 或 Luna 的指引，可能过度约束 GPT-6 Astra——留下指令时要想清楚会被哪些模型用到。

## 保持 AGENTS.md 常新

AGENTS.md 在模型于仓库工作时始终生效，应常重审每条指令是否还需要。

- 每次编辑前都强制读一摞文档或整仓地图，对改错别字来说过重。GPT-6 Astra 能自己判断该读什么。
- 坏：「每次编辑前先读 architecture.md、database.md、deployment.md。」
- 好：「看服务边界用 architecture.md；改 schema 用 database.md；准备部署时用 deployment.md。」
- 以前的模型需要鼓励才会跑测、自查；GPT-6 Astra 会自己做，同一套指令可能导致多余测试。
- Astra 很仔细，但对「任务该做到哪」可能更犹豫，有时需要轻轻推一把。可用 AGENTS.md 给已知安全的工作流放权，例如：「本地测试用一次性 fixture，无生产访问。请跑测、修复由本次请求改动引起的失败，并重跑受影响测试，不必每步征求批准。」

## 决策边界

以前的模型未经许可就代你做事，你可能加过强硬措辞逼它先问。GPT-6 Astra 作为对齐最好的模型之一，判断力强得多，不确定安全就不会做。若边界是为防其他模型越界而写、现在切到 Astra，考虑更新措辞——Astra 可能过于当真，在你其实希望它继续的地方停住。

## 坚持做完

Astra 对「何时停」可能更犹豫——可能刚到第一版实现就回来请你审，而活还没做完。

对策：开工前**定义完成标准**。若任务包含跑通实现、检查结果、修失败，就把这些写进请求。「第一版实现后必须停下等审」会把模型拉向更早的停点——确认这是否真是你需要的决策。若希望第一遍之后继续探索，说清要探索什么、停在哪里。

新模型是打扫屋子的好时机，但不必事事手审：让 GPT-6 Astra 按本文讨论做一次审计（哪些 skill 描述过长、哪些 AGENTS.md 指令已过时、哪些边界措辞需要更新），然后去做以前不敢尝试的东西。
